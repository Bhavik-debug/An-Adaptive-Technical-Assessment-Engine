# Turn API, idempotency, background grading and SSE (Day 22)

Plan §3, Day 22: *"Turn API: `POST /sessions/{id}/turns` with a client-supplied
`turn_id`, `INSERT ... ON CONFLICT DO NOTHING` for idempotency, `202 + SSE`

(submission), `backend/app/interview/grading.py` (worker),

## 1. The flow in one picture

```
client                          API (FastAPI)                       Postgres                      worker
  │ POST /turns {turn_id, answer} │                                    │                             │
  │──────────────────────────────►│ lock session row, look up turn_id  │                             │
  │                               │ new → stage ANSWER_SUBMITTED,      │                             │
  │                               │       INSERT turn (pending),       │                             │
  │                               │       COMMIT ─────────────────────►│ turn + event, atomically    │
  │◄──────── 202 {status:pending} │ cache new state (best effort)      │                             │
  │                               │                                    │◄── claim (SKIP LOCKED) ─────│
  │ GET /stream (SSE)             │                                    │    commit claim, attempt=1  │
  │──────────────────────────────►│ poll max(seq) every 0.5 s          │                             │ grade_answer()
  │◄── event: grading_started ────│                                    │                             │ (LLM, no DB held)
  │                               │                                    │◄── fenced COMMIT: ──────────│
  │                               │                                    │    ANSWER_GRADED + turn     │
  │                               │                                    │    result + session cost    │
  │◄── event: grade_ready ────────│                                    │                             │
```

*Day 22 as built:* the session stayed in `GRADING` (graded) after the grade.
**Day 23 update:** the same transaction that commits the grade now also commits
the decision: a follow-up, the stop rule, or the next item. See
[follow-ups.md](follow-ups.md).

## 2. Routes

All routes require `Authorization: Bearer <access token>` (Day 2). A missing or
invalid token is `401`. A session that does not exist **or belongs to someone
else** is the same `404 {"detail": "Session not found"}`, so ids cannot be probed.

### 2.1 `POST /api/sessions/{session_id}/turns`

Request (unknown fields are rejected, so a client **cannot** send a score):

```json
{ "turn_id": "6f1c…-uuid", "answer": "I would cache the rendered row …" }
```

| Field | Rule |
|---|---|
| `turn_id` | UUID, generated by the client **once per answer**, re-sent unchanged on every retry |
| `answer` | 1–8000 characters (`app.grading.grader.MAX_ANSWER_CHARS`), not only whitespace |

Response body (`TurnStatus`):

```json
{
  "session_id": "…", "turn_id": "…", "question_id": "dsa-001",
  "status": "pending", "attempts": 0, "score": null, "error_code": null,
  "submitted_at": "2026-10-11T05:48:23Z", "graded_at": null,
  "status_url": "/api/sessions/…/turns/…", "stream_url": "/api/sessions/…/stream"
}
```

| Outcome | Status | Notes |
|---|---|---|
| New turn accepted | **202** | `Location: <status_url>`. Accepted, **not graded**. |
| Same `turn_id`, same answer (a retry) | **200** | The original turn, whatever its status now; `Idempotent-Replayed: true`; nothing written |
| Same `turn_id`, different answer | **409** | "turn_id was already used for a different answer; generate a new turn_id"; nothing written |
| Session not in `ASKING` (e.g. still grading the last answer) | **409** | `IllegalTransition` |
| The current question is a follow-up asked **without stored wording** (only a pre-Day-23 log) | **409** | Day 23: follow-ups asked by the worker carry their text and are accepted like any question |
| Log moved concurrently | **409** | `SeqConflict` |
| Invalid body | **422** | FastAPI's standard validation response |
| Not yours / does not exist | **404** | |
| Event log corrupted | **500** | "Session state unavailable"; logged as an error |

### 2.2 `GET /api/sessions/{session_id}/turns/{turn_id}`

This returns the same `TurnStatus`. It is the polling alternative to the stream.

### 2.3 `GET /api/sessions/{session_id}/stream`

This is a server-sent event stream; see §6. Optional header: `Last-Event-ID: <seq>`.
A malformed header returns `400`.

### 2.4 Status values

`status` describes the **background grading job** for one turn. These are not
FSM states: the session is in `GRADING` the whole time.

| `status` | Meaning | `score` | `error_code` |
|---|---|---|---|
| `pending` | Accepted and durable; waiting for a worker, or waiting out a retry backoff | null | null, or the last *transient* error being retried |
| `processing` | A worker has claimed it and is grading | null | as above |
| `graded` | A valid grade is committed | the score in [0, 1] | null |
| `failed` | No valid grade: a permanent error, or retries used up | null | a machine code (§5.3) |

### 2.5 Example

```bash
TOKEN=<access token from POST /api/auth/login>
SID=<session id>
TURN=$(python -c "import uuid; print(uuid.uuid4())")

curl -i -X POST "http://localhost:8000/api/sessions/$SID/turns" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d "{\"turn_id\": \"$TURN\", \"answer\": \"<your answer>\"}"          # 202

curl -s "http://localhost:8000/api/sessions/$SID/turns/$TURN" -H "Authorization: Bearer $TOKEN"

curl -N "http://localhost:8000/api/sessions/$SID/stream" -H "Authorization: Bearer $TOKEN" \
  -H "Last-Event-ID: 2"
```

*Day 23 update:* `POST /api/sessions` and `POST /api/sessions/{id}/start` now
exist ([follow-ups.md](follow-ups.md) §6), so a whole session can be driven
over HTTP.

## 3. Idempotency

**Key:** `(session_id, turn_id)`, enforced by the Day-2 unique constraint
`uq_turns_session_id_turn_id`.

**The submission transaction** (`app/interview/turns.py::submit_turn`):

1. `SELECT … FROM interview_sessions … FOR UPDATE`. This checks ownership and
   takes a per-session lock, so all writes to one session queue behind each other.
2. Look up `(session_id, turn_id)`. If it exists, **stop here**:
   * same answer → return the original turn (200), write nothing;
   * different answer → `TurnIdConflict` (409), write nothing.
3. Stage `ANSWER_SUBMITTED {turn_id}` through Day 21's `stage_append`, which
   folds the log and lets the FSM decide legality.
4. `INSERT INTO turns … ON CONFLICT (session_id, turn_id) DO NOTHING RETURNING id`.
5. `COMMIT`. The turn and its event become visible together or not at all.
   Only after that does the cache update run (Day 21's `commit_and_cache`).

The duplicate check runs **before** the FSM check on purpose. A retry that
arrives after the session has moved to `GRADING` must get the original turn
back, not "not allowed from GRADING".

**Concurrency.** Simultaneous duplicates are serialised by the row lock: the
first commits, and the rest then find its turn. `ON CONFLICT DO NOTHING` is the
backstop for any path that might insert without the lock. In that case the
insert returns no row, the transaction is rolled back (taking its staged event
with it), and the caller re-reads and returns the winning turn. A test removes
the lock to prove this path works.

**What counts as "the same request".** The stored answer is compared with the
submitted one **exactly**, with no normalisation. Even a single trailing space
makes it a different submission and returns 409. Guessing which differences
"don't matter" is how an idempotency key ends up returning a grade for an
answer nobody gave. Neither answer is ever logged.

## 4. Background grading

### 4.1 Why `turns` is the queue

The plan names **arq** for background work (§13.1), but nothing in the
repository installed it, and there is no other queue. Rather than add queue
infrastructure, the turn row records its own grading lifecycle (migration
0004), and workers claim rows from Postgres:

```sql
UPDATE turns SET grading_status='processing', grading_attempts=grading_attempts+1,
                 lease_expires_at = now() + <timeout + 60 s>
 WHERE id = (SELECT id FROM turns
              WHERE (grading_status='pending' AND (next_attempt_at IS NULL OR next_attempt_at <= now()))
                 OR (grading_status='processing' AND lease_expires_at < now())
              ORDER BY created_at, id
              FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING id;
```

* **Durable.** A `202` is only returned after the turn row commits. If the API
  crashes, the row is still `pending`, and the next worker to start grades it.
  A test stops the app before grading, starts a new app, and checks that the
  turn gets graded.
* **One owner per row.** `SKIP LOCKED` gives each row to exactly one of many
  polling workers, and none of them blocks on another. A test with six
  competing workers confirms exactly one claim.
* **No DB held during the LLM call.** The claim commits before the model is
  called.
* **The worker runs inside the API process** (started in the FastAPI lifespan,
  `GRADING_WORKER_ENABLED=true`). Because it keeps no state of its own, it can
  later be moved into a separate process unchanged (`run_worker` takes a
  sessionmaker, a cache and a policy).

### 4.2 What a success writes — one transaction

Under the session lock, after the **fence** check (§4.4):

* `ANSWER_GRADED {turn_id, score, ability}`. Here `ability` is the subtopic's
  state after Day 11's `update_ability` (prior: `Blueprint.prior_ability()`),
  with `grader_confidence` as `f_conf` and the bank-item stake.
* On the turn: `grading_status='graded'`, `score`, `grader_confidence`,
  `latency_ms`, `graded_at`, and `grade`, which holds the judgment, breakdown,
  confidence-gate record and per-call metadata. It never holds the prompt.
* On the session: `cost_usd += Σ cost`, `total_tokens += Σ tokens` (§7).

The grade itself comes from `app.grading.pipeline.grade_answer`, **unchanged**:
all four passes and the confidence gate. The worker never reads a score from
the client; the request schema has nowhere to put one.

### 4.3 Retry policy

| Setting | Default | Meaning |
|---|---|---|
| `GRADING_MAX_ATTEMPTS` | 3 | total claims of one turn, **including claims lost to a crash** |
| `GRADING_RETRY_BASE_S` / `GRADING_RETRY_MAX_S` | 2 / 30 | backoff `min(max, base·2^(attempt−1))` → 2 s, 4 s, … capped |
| `GRADING_TIMEOUT_S` | 300 | wall clock for one attempt (up to 4 chokepoint calls) |
| lease | timeout + 60 s | how long a claim is honoured before another worker may take over |
| `GRADING_POLL_INTERVAL_S` | 1 | idle poll |

This is an **outer** layer of retries. The chokepoint already retries each
provider (`LLM_MAX_ATTEMPTS_PER_PROVIDER`), fails over between providers, and
repairs schema errors. A failure that reaches the worker has survived all of
that.

### 4.4 Fencing: why a slow worker cannot double-grade

A worker may only finish the attempt it claimed. The finishing transaction
re-reads the turn `FOR UPDATE` and continues only if the turn is still
`processing` **at the same `grading_attempts`**. Consider worker A, which
stalls past its lease while worker B re-claims the turn (attempt 2). When A
finally wakes up, it finds the attempt number has moved on and discards its
result. A test runs exactly this interleaving, with A finishing first. A
mutation test confirmed that this test fails when the fence is removed.

### 4.5 Failure representation (Decision C)

| Classification (`classify_error`) | Retried? | `error_code` |
|---|---|---|
| `ProviderTimeoutError`, `ProviderRateLimitedError`, `ProviderUnavailableError` (`retryable=True`) | yes, bounded | `provider_timeout`, `provider_ratelimited`, `provider_unavailable` |
| `AllProvidersFailedError` (router exhausted every provider) | yes, bounded | `all_providers_failed` |
| `TimeoutError` (incl. `GRADING_TIMEOUT_S`), `ConnectionError` | yes, bounded | `timeout`, `connection_error` |
| `ProviderAuthError`, `ProviderBadRequestError`, `ProviderResponseError` | no | `provider_auth`, `provider_badrequest`, `provider_response` |
| `SchemaValidationFailedError` (after the chokepoint's own repairs) | no | `schema_validation_failed` |
| `GradingInputError` / `GradingContractError` | no | `ungradeable_input` / `grader_contract_violation` |
| `LLMConfigError`, `PromptNotRegisteredError` | no | `llm_misconfigured` |
| anything else (logged with a traceback) | no | `internal_error` |
| claimed again after crashes used up the attempts | — (model not called) | `retry_exhausted` |
| the log refuses the grade (turn no longer current) | no | `state_conflict` |
| the question row is gone | no | `question_unavailable` |

A transient error with attempts remaining → `pending` with a backoff, no event.
A permanent error, or attempts used up → **one transaction** that sets the turn to
`failed` and appends:

```json
GRADING_FAILED {"turn_id": "…", "error_code": "provider_timeout", "attempts": 3, "retries_exhausted": true}
```

`GRADING_FAILED` is a **self-loop in `GRADING`**, not a new state (Decision C).
The session stays in `GRADING` with the turn ungraded, which is exactly true.
No `ANSWER_GRADED` is written, no ability changes, and no cost is applied.
Because it is in the log, replay and SSE both see it. Leaving `GRADING` still
requires a grade, so a failed turn cannot be skipped by accident.

**Recovery:** `app.interview.grading.requeue_failed_turn(maker, session_id=…,
turn_id=…)` is an operator action, for use once the cause (an outage, a bad key)
is fixed. It resets the turn to `pending` with a fresh attempt budget. A later
`ANSWER_GRADED` is legal after a `GRADING_FAILED`. There is no HTTP route for it.

Diagnostics stored: the turn's `grading_status`, `grading_attempts`,
`grading_error`, `next_attempt_at` and `lease_expires_at`, plus the event.
Provider messages are **not** stored, because they can quote the request,
which contains the answer. The worker logs the exception *type* and the code.

## 5. SSE

### 5.1 Wire format

Every message is built from one durable `interview_events` row:

```
id: 4
event: grade_ready
data: {"score":0.875,"seq":4,"state":"GRADING","turn_id":"…"}

```

| Log event | SSE `event` | `data` beyond `seq`, `state` |
|---|---|---|
| `ANSWER_SUBMITTED` | `grading_started` | `turn_id` |
| `ANSWER_GRADED` | `grade_ready` | `turn_id`, `score` |
| `GRADING_FAILED` | `grading_failed` *(Day 22 addition)* | `turn_id`, `error_code`, `retries_exhausted` |
| `QUESTION_ASKED` | `next_question` | `question_id`, `is_follow_up`, `text` *(Day 23)* |
| `FOLLOW_UP_STARTED` | `follow_up` *(emitted from Day 23)* | — (deliberately nothing) |
| `FOLLOW_UP_ABANDONED` | `follow_up_abandoned` *(Day 23)* | `error_code`, `retries_exhausted` |
| `SESSION_COMPLETED` | `session_complete` *(reserved: nothing emits it before Day 25)* | — |
| anything else | `state_changed` | `event_type` |
| — (log unreadable) | `error` | `code: "session_state_unavailable"`; then the stream ends |

`data` is a **whitelist projection**, not the payload. It never contains the
answer, the judgment, evidence spans, ability snapshots, stop or follow-up
reasons, prompts, or provider messages. It is capped at 8 KB per message (2 KB
on Day 22; raised on Day 23 for a 2000-character question `text`), and
`: keepalive` comment lines are sent every `SSE_KEEPALIVE_S` (15 s) while idle.

*Day 22:* `next_question` carried only the `question_id`. *Day 23:* it also
carries `text`, the wording shown, which is now stored in `QUESTION_ASKED`.

### 5.2 Reconnection and replay

`id` is the event's `seq`, which is permanent and gap-free. A client that
reconnects with `Last-Event-ID: N` receives every event with `seq > N`, in
order: nothing twice, nothing missed, whatever happened while it was away.
Browsers' `EventSource` sends this header automatically. Without the header,
the stream replays the whole log from seq 0. A test disconnects, lets a turn
get submitted and graded, reconnects with the last id, and receives exactly
the missed events.

### 5.3 How it waits, and when it ends

The stream polls `max(seq)` every `SSE_POLL_INTERVAL_S` (0.5 s), and each poll
uses its own short-lived DB session, so an idle stream holds no connection.
Pub/sub (e.g. Redis) would cut latency, but it would also lose messages
published during a reconnect gap; that would need the log for replay anyway,
so polling the log was chosen. The stream ends after `session_complete`, on
client disconnect (`request.is_disconnected()`), or when the session
disappears. Ownership is checked before the response starts (so a stranger
gets a real 404) and again on every poll.

## 6. What "charge" means in this repository

The Phase-5 gate says *"double-submitting a turn produces exactly one grade and
one charge."* Before implementing anything, the repository was searched for
anything that charges:

| Looked for | Found |
|---|---|
| Plans, subscriptions, `usage_counters`, `billing_events`, payments | **Nothing.** Phase 8 (Days 36–40). |
| Quotas or metering | **Nothing.** |
| Per-call LLM cost | `CallMeta.cost_usd` and token counts on every chokepoint call (`app/llm/client.py`, `pricing.py`). Logged and traced, never persisted. |
| A persisted per-session total | `interview_sessions.cost_usd NUMERIC(10,6)` and `total_tokens INT`, created on Day 2 ("money-adjacent and gets summed"). **Nothing wrote them before Day 22.** |

So, based on what actually exists, **"charge" here means applying one grade's
LLM cost and tokens to its session's `cost_usd`/`total_tokens`**. That is the
only accounting the codebase has. It is not a monetary debit to the
candidate, and no price, plan or billing table was invented.

**How it is kept to at most one per logical turn.** It is applied in the same
transaction as `ANSWER_GRADED` and the turn's `graded` status. That transaction
commits only if the attempt fence holds and the FSM accepts the grade, and the
FSM refuses a second grade for the same turn. So one logical turn leads to at
most one committed grade, which leads to at most one cost application. Retries,
duplicate deliveries and competing workers were tested; a test-only counter
(clearly labelled as instrumentation) confirms that the accounting path runs
exactly once.

**What it does not cover:**

* **Provider calls are not exactly-once.** A crash between the model's answer
  and the commit, a fenced-out stale worker, or a transient-error retry each
  mean the provider is called again. No design can make an external HTTP call
  and a DB commit atomic. This one makes the *committed* outcome unique, and
  keeps duplicate calls bounded by `GRADING_MAX_ATTEMPTS`.
* **The cost of attempts that never succeeded is not accounted.** A failed
  call raises, and the exception does not carry its `CallMeta`. That spend is
  visible only in logs and traces. Recording it belongs with Phase 8's metering.

## 9. Limitations and deferred work

* ~~No session-creation or first-question route~~ — **resolved on Day 23.**
* ~~The session stops at `GRADING` (graded)~~ — **resolved on Day 23**: the
  decision is committed with the grade.
* ~~Follow-up answers are refused~~ — **resolved on Day 23**, except for
  follow-ups without stored wording (pre-Day-23 logs only).
* **No cancellation (Decision B).** There is no `/end` route and no
  `ABANDONED`/`CANCELLED` state. A session can only end through the stop rule.
* **A `failed` turn blocks its session until an operator re-queues it.** There
  is no automatic way forward: skipping a turn is a policy decision nobody has
  made.
* **The worker runs inside the API process.** That is correct (durable queue,
  leases, fencing) but it shares CPU with request handling. Moving it to its
  own process is a deployment change, not a code change.
* **Questions ingested before Day 22 have no misconceptions** until the bank is
  re-ingested (`python scripts/ingest_question_bank.py`). Until then they are
  graded without that input, as `grade_answer` allows. The local dev database
  is in this state (60 questions, 0 with misconceptions).
* **No rate limiting on the submission route** (plan §14 puts rate limits on
  Day 30).
* **Failed-attempt spend is not accounted** (§6).
